# PC Builder & Store — persistent project context

**Статус (27.10.2026):** согласованы функциональность, дизайн-референсы и стек; работающего кода ещё нет. Это **запланированный продукт**, а не описание найденного runtime. Перед существенными задачами проверить фактические локальные файлы и обновить только подтверждённые изменения.

## Цель

Полноценный, убедительный Full-Stack-проект для портфолио: каталог комплектующих и готовых ПК, 2D-конфигуратор с проверкой совместимости, корзина, личный кабинет, приватные сохранённые сборки и история **демонстрационных** заказов. Приоритет — качество, проверяемость и быстрое завершение, а не искусственное наращивание функционала.

## Утверждённый стек

- Frontend: **React, TypeScript, Vite, Tailwind CSS, Zustand, Zod, React Router, TanStack Query, Orval**; React Hook Form допустим для форм.
- Backend: **Python, FastAPI, Pydantic, SQLAlchemy 2.x, Alembic, psycopg, PyJWT, pwdlib + Argon2**.
- Данные: **PostgreSQL**, поиск **PostgreSQL Full-Text Search + pg_trgm**.
- Запуск: **Docker + Docker Compose** (локально), исходники/демо — **GitHub**.
- Проверки: **Vitest, React Testing Library, pytest, HTTPX**; **Playwright, GitHub Actions** — опционально по задаче.
- Redis — опционально позднее, только после согласованного решения; для старта не нужен.

## Режим работы / конвейер

1. Реализовать frontend по референсам с Mock API и согласованными контрактами.
2. Реализовать FastAPI + PostgreSQL, бизнес-логику, auth, данные, тесты.
3. Интегрировать OpenAPI FastAPI через Orval для TypeScript/Zod/API-клиента и TanStack Query.
4. Проверить frontend/backend/end-to-end, подготовить Docker Compose, README, воспроизводимый локальный запуск и GitHub-портфолио.

## Навигация (подтверждено)

- `/` — главная.
- `/catalog` — общий каталог, фильтры и поиск, включая готовые ПК.
- `/products/:slug` — страница товара.
- `/cart` — корзина.
- `/builder` — **2D** конфигуратор.
- `/account` — профиль.
- «Мои сборки» и «Мои заказы» — приватные разделы, **точные пути пока не утверждены**; не придумывать окончательные URL без задачи.
- Вход и регистрация — **модальные режимы одного окна**, не отдельные страницы.

## Не менять без явного решения

- 3D/WebGL/GLB отменены. Только 2D список деталей с выбором/заменой.
- Сравнение отменено полностью: никаких `/compare`, кнопок и преимуществ с этой функцией.
- Публичные готовые сборки являются **обычными товарами** категории `prebuilt` в `/catalog`, не `/builds`.
- Сохранённые пользовательские сборки **приватные**; сервер обеспечивает ownership/authorization, не только frontend.
- `/checkout` отменён: «Купить» → простой «Спасибо!» без форм оплаты/доставки, демонстрационная запись заказа.
- Никакого VPS/платного деплоя по умолчанию; GitHub + локальная демонстрация.
- «Блог» удалён из запланированного меню.

## Дизайн-система

**Основная тёмная тема: Obsidian Black + Ice Blue**. Фон `#08090C`, Header/Footer `#0E1015`, карточки `#14171D`, границы `#252932`, основной текст `#F5F6F8`, вторичный `#9298A5`, акцент `#67C9FF`.

**Светлая тема:** светлые/белые поверхности, тёмные надписи, синий акцент. Светлые референсы служат образцами; не переносить случайные несовместимые элементы между темами. Итоговый рендер обязательно проверять.

## Core invariants

- Фиксированный Header и общая навигация; общие состояния UI — Zustand, серверные данные/кеш — TanStack Query.
- Поиск по всем товарам на сервере (Full-Text Search + pg_trgm), включая готовые сборки; в mock-этапе — аналогичный контракт.
- Каталог: **49 товаров/страница** (7 колонок × минимум 7 строк при заполненной странице на максимально широком desktop); неполная последняя строка по центру, адаптивность на меньших экранах.
- Фильтры зависимые: master-категория → тип → цвет/производитель, сброс зависимых значений при изменении родителя.
- Корзина считает пользовательскую сборку **одной позицией**, с раскрываемым составом; не суммирует вложенные компоненты повторно.
- Создаваемые/сохранённые сборки строго приватны; проверки совместимости и права доступа — настоящие правила backend, не UI-условности.
- История демонстрационных заказов приватна; цены/количества/состав покупки должны храниться как snapshot на момент оформления, а не пересчитываться на текущем каталоге.
- Периоды, цены, товары, наличие и статусы на референсах — вымышленные примеры, не реальные API-данные.
- **Деньги всегда в RUB.** Все суммы (БД, API, корзина, сборки, заказы) хранятся и считаются в рублях. Валюта отображения — только презентация: `formatMoney`/`convertRubToMinorUnits` (BigInt, округление один раз на границе вывода), RUB-ветка делегирует в `utils/formatPrice.ts`. Пересчитанные значения никогда не отправляются на backend и не участвуют в сравнениях/сортировке. Исторические заказы и админка остаются в RUB.
- **Курсы ЦБ РФ** — `GET /api/v1/currency/rates` (публичный, без БД и без авторизации), источник — `app/services/currency_rates.py`: один процесс-локальный snapshot (TTL 1 ч на `time.monotonic()`, stale-фоллбэк, cooldown 60 с после сбоя), `Decimal`-нормализация `Value/Nominal`, 503 при отсутствии валидного snapshot. Фронтенд: один общий TanStack-ключ, включён только для не-RUB, строгая Zod-валидация ответа, выбор валюты — `pc-builder-currency` в localStorage.
- **Тема**: `dark:`-утилиты Tailwind в этом проекте привязаны к `prefers-color-scheme`, а не к классу `.dark`; тема приложения переключается CSS-переменными. Для тематических поверхностей использовать токены (`bg-surface`, `--color-primary-light`), а не `dark:`-варианты.
- Header: порядок — меню, логотип, поиск, язык, валюта, корзина, профиль; шаг между контролами `gap-3`.

## Обработка ошибок уровня страницы (утверждено, реализовано)

- **Одна страница на пять статусов.** `components/error/ErrorPage.tsx` — единый полноэкранный компонент для `403 | 404 | 429 | 500 | 503` (`api/errorStatus.ts`, `ErrorStatus`). Другие статусы (400/401/408/409/422/502/504) и сетевые сбои (`ApiError` со `status: 0`), отмены и ошибки схемы Zod **никогда** не становятся полноэкранной страницей — они остаются локальными.
- **Классификация одна.** `errorPageStatus(error)` переиспользует существующий `ApiError` из `api/transport.ts`; второй транспортный слой и глобальный интерсептор не создаются. Для запросов, без которых страница невозможна, используется одна функция `primaryQueryErrorStatus(query)`: полноэкранная страница включается только при `isError && data === undefined`. Сохранённые данные после неудачного фонового refetch и успешный пустой ответ ошибкой не считаются. Локальная ветка ошибки списка товаров в `CatalogPage` использует то же условие — `products.isError && products.data === undefined`, — поэтому неудачный фоновый refetch не скрывает уже показанную страницу каталога. Ключи локализации собирает `errorStatusKey`, тексты лежат одним блоком `error_page` в `i18n/locales/ru.errors.json` / `en.errors.json` (объединяются в `i18n/index.ts`).
- **Где рендерится.** Wildcard `/`→`NotFound` (404); страница товара без данных; `AdminGate` при явном 403 и при недоступной проверке прав (429/500/503 **без подтверждённых данных** — до первого успешного ответа); первичные запросы `CatalogPage` (`products`), `CartPage` (корзина `useServerCart`), `OrdersPage` (список заказов), `SavesPage` (список сборок); граница ошибок рендера (`RouteErrorBoundary`, 500) вокруг `<Routes>` внутри `BrowserRouter`. В `OrdersPage`/`SavesPage` запрос поднят в наружный компонент, чтобы полноэкранная страница заменяла Header/Footer, а не рендерилась внутри них. Выделенных `/error/404`-маршрутов нет, URL не меняется.
- **Граница ошибок.** `ErrorBoundary` сбрасывается по `resetKey = location.key + pathname + search`: переход на валидный маршрут выходит из состояния ошибки, и осознанный переход на **тот же** URL (например, «На главную» на уже открытом `/`) тоже даёт странице новый шанс отрендериться. Обычный rerender ключ не меняет, поэтому ошибка не переигрывается. Вложенная граница с простейшим запасным вариантом исключает рекурсию.
- **Навигация «Назад».** `navigation/internalHistory.ts` + `navigation/InternalHistoryProvider.tsx` — небольшой трекер уровня роутера: `PUSH` добавляет запись, `REPLACE` заменяет текущую и не создаёт предыдущую, `POP` восстанавливает только уже известную запись, неизвестный `POP` (перезагрузка, чужой документ) считается отсутствием истории. Кнопка «Назад» возвращает в известную внутреннюю страницу через `navigate(-1)` (POP, без новой записи); если известной записи нет или она сама показывала ошибку — `navigate('/', { replace: true })`. `location.key !== 'default'`, `window.history.length` и `document.referrer` доказательством не считаются. Маркеры «эта запись показывала ошибку» живут ровно столько же, сколько их записи истории: `record()` сбрасывает маркеры всех отброшенных записей (`PUSH`-truncate, `REPLACE`, лимит в 100 записей, сброс неизвестным `POP`), а `reportHealthyEntry()` снимает маркер, когда та же запись снова рендерит нормальный контент. Размонтирование `ErrorPage` освобождает только claim своей записи и маркер не снимает: уход со страницы ошибки не считается восстановлением. Claim пишется эффектом страницы, который React выполняет раньше эффектов провайдера (дети раньше предков), поэтому только что смонтированная страница ошибки не теряет маркер из-за порядка эффектов; под StrictMode цикл setup→cleanup→setup идемпотентен.
- **Тема и шрифты.** Ошибка использует тот же механизм темы (`.dark` на `<html>`, `bg-surface-2` = `#08090C` в тёмной), но свои локальные CSS-переменные `--pc-error-*` в `components/error/ErrorPage.css`. Шрифты подключены локально только в этом компоненте (`Tektur Variable` 700 — заголовок извинения, `Inter Variable` 600 — статус и кнопки, 400 — описание, **900 — числовой код**); глобальная типографика магазина не менялась. `Russo One` установлен, но на страницах ошибок не используется.
- **Метрики кода.** Цифры набраны Inter 900; размер и вертикальный сдвиг подобраны под метрики Inter, чтобы полоса краски совпадала с референс-кадром (21.25 % – 36.98 % высоты при 1440 px): `font-size: min(20.55vh, 11.56vw)`, `top: 4.04vh` внутри сцены.
- **Блок текста.** Статус и описание обёрнуты в `.pc-error-page__text` с внешними отступами `1.39vh` (≈20 px при 1440) сверху и `2.08vh` (≈30 px) снизу и `0.42vh` (≈6 px) между заголовком статуса и описанием; индивидуальные отступы этих элементов обнулены, чтобы воздух не суммировался. Числовой код — абсолютный слой, поэтому его `top` увеличен на те же `0.69vh` (≈10 px): без этого увеличенный нижний отступ блока не дал бы видимого зазора. Итоговый видимый зазор описание → краска цифр ≈ 26 px при 1440, полоса краски кода 21.93 % – 37.67 % высоты.
- **Композиция.** Слой иллюстрации (`z-index: 0`) и отдельный элемент кода (`z-index: 1`) в одном `isolation: isolate` контексте: дым остаётся частью PNG и уходит за цифры. Размеры/отступы — доли референс-кадра (1671×941), в `vh`/`vw`.
- **Модальное окно входа.** Страница регистрируется через `FullscreenErrorContext`; `App` не рендерит `AuthModalHost`, пока регистрация активна, и эффект `FullscreenErrorModalGuard` закрывает модалку через `useUIStore.closeAuthModal()`, а также следит за самим флагом `authModalOpen`, поэтому программно открытая во время ошибки модалка тоже не оставляет устаревшего состояния и не всплывает после ухода со страницы ошибки. Счётчик регистраций сбалансирован в StrictMode; аккаунт, сессия, кеш запросов, тема, язык и валюта не затрагиваются.
- **Что осознанно осталось локальным:** скелетоны, сохранённые данные после неудачного фонового refetch, формы и 422, 401, мутации (корзина, оформление, сборки), опциональные запросы (отзывы, избранное, фильтры, подсказки), проверки совместимости сохранённых сборок, админский retry для статусов вне списка и **RUB-фоллбэк при 503 курсов ЦБ**.
